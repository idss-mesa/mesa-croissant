# Roadmap

## Version 1 (current)

Convention version 1, `core.py` 1.3.0 (1.1.0: review fixes, `transformJsonPath`, file
import; 1.2.0: unknown keys and duplicates kept with their entity, `UNKNOWN_KEY`; 1.3.0: a
duplicate list index kept on the leaf it duplicates, `DUP_KEY`). The design is in [DESIGN.md](DESIGN.md) and the contract in
[AVU_CONVENTION.md](AVU_CONVENTION.md).

In scope:

- **AVU convention.** The `croissant.*` convention for Croissant Core 1.1, RAI 1.0 and
  GeoCroissant 1.0: dataset, persons, RAI, geo, distribution (FileObject / FileSet), the file
  itself, record sets, fields and one level of subfields.
- **`mesa_croissant.core`.** The pure-stdlib codec (AVUs ⇄ model ⇄ JSON-LD), the read-only
  MESA crosswalk from `datacite.*`, `dc.*`, ontology and `mesa.*` AVUs, tolerant import of
  Croissant 0.8, 1.0 and 1.1 (including the Hugging Face, Kaggle and OpenML dialects), the
  structural validator, the encoding-format and DuckDB / Arrow type maps, and the
  distribution suggestions for folders and DuckLake projects.
- **Fixtures.** Golden fixtures shared with the portal, and pinned upstream examples.
- **mlcroissant check.** An optional mlcroissant 1.1.1 compatibility test, with the
  `keyword_style="text"` escape hatch, and a record-loading check of the record set both
  writers build for one schema (`schema_parity.json`, shared with the portal).
- **MESA-MCP plugin.** `mesa_croissant_template`, `_export`, `_validate`, `_apply`
  (merge / replace, dry run by default, one DuckLake snapshot per write, file documents
  imported as `croissant.file.*`, generated values left out as the portal's importer does)
  and `_from_schema` (STRUCT members with `transformJsonPath`), on surface `croissant`.
- **mesa-mcp reserved prefix.** `croissant` is reserved in ontology detection, and the
  `mesa_croissant_` prefix maps to the `croissant` surface.
- **MESA Portal.** The vendored core; the Croissant tab of the metadata page (overview
  structure map, dataset / RAI / geo / distribution / record-set forms, JSON-LD preview,
  import and download); the four `data/croissant/` endpoints; the folder-header chip; and the
  DuckDB viewer hand-off.

## Follow-ups (out of scope for version 1)

Each item becomes a GitHub issue.

1. **Public Croissant for search engines.** Anonymous reading of Croissant on public paths,
   and `<script type="application/ld+json">` on public pages for Google Dataset Search. This
   needs a public AVU read path; today `GET /data/metadata/` is login-only.
2. **`croissant.json` sidecar.** A file written next to the data, generated from the AVUs, for
   tools that look for a file rather than an API.
3. **Server-side schema inference.** Parquet / CSV schema inference (croissant-baker style)
   without the DuckDB viewer, so folders get record sets without a browser session.
4. **Full `mlcroissant` validation in the portal.** It is a heavy dependency (pandas, scipy,
   rdflib, networkx). It could run as a sidecar or a background job instead.
5. **Eclair and croissant-baker interoperability.** MCP interoperability with Eclair and
   croissant-baker beyond the documented recipes: for example, importing croissant-baker
   output through `mesa_croissant_apply`, or letting Eclair discover MESA datasets.

Smaller items noted during version 1:

6. **Nested subfields.** Done in core 1.1.0: `transformJsonPath` carries Hugging Face's
   `transform.jsonPath` (and the STRUCT member path MESA tools write). Deeper nesting than
   one subField level is still written as `sc:Text` by MESA tools.
7. **mlcroissant DefinedTerm keywords.** mlcroissant 1.1.1 still rejects `sc:DefinedTerm`
   keywords. The portal's "use this dataset" snippet already downloads with
   `keywords=text`; decide whether `keyword_style="text"` becomes the default for the plain
   download and `mesa_croissant_export` too.
8. **SHA-256 checksums.** When the Data Store stat has a `sha2:` checksum, use it as the file
   FileObject's `sha256` (today only MD5 checksums are used).
9. **DOI source in MESA-MCP.** `mesa_croissant_apply` knows an item's DOI only from its
   `datacite.identifier` AVU; the portal also reads its DOI records. A DOI minted in the
   portal without that AVU is not recognised as generated by the MCP importer.
